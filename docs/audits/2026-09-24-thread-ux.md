# Solenta thread and interaction audit

Date: 2026-09-24. Audited checkout: `bd04a856`, `release/0.21.1`.

Recommendation: organize the sidebar around the user's task, with workers inside that task. Make outcomes and decisions prominent, then use short motion to explain changes in that structure.

Evidence: the supplied sidebar screenshot; sidebar, fork creation, waiting, settling, team/integration, transcript, composer, navigation and theme source; current primary sources from T3 Code and Stably's Orca. Live Solenta window inspection was denied by Computer Use. This is a source-grounded design audit, not a full desktop usability or performance test. The supplied screenshot contains another project's task; no other project's threads or stored transcripts were accessed. Prototype content is illustrative.

Tracked in [audit issue #1341](https://github.com/currentbits/solenta/issues/1341). The findings below describe the audited base. Implementation progress is recorded separately here so the original evidence remains distinguishable from the updated app.

## What is making threads feel messy

| Finding | Evidence | Consequence |
| --- | --- | --- |
| Generated names accumulate `Fork:` indefinitely. | `electron/services.js:1202`, especially title creation at 1248. `forkWorkerThread` calls that same path. | The title eventually describes ancestry rather than the work. |
| Manual forks and delegated workers share the same sidebar treatment. | `src/sidebarGroups.ts:261` attaches all `handoffFrom` links; the worker flag is not consulted. | Different relationships look identical. |
| Every descendant is rendered as a substantial thread card. | `Sidebar.tsx:2277` onwards; `.card` has a 64px minimum and `nested` is one boolean (`Sidebar.module.css:490,526`). | A large crew dominates the list. Grandchildren look like siblings, with no family disclosure. |
| Settling does not reliably remove descendants from their visible family in this checkout. | `buildFlatSidebar` pulls settled descendants back under active/pinned ancestors (`sidebarGroups.ts:193` onwards). | Old work continues to consume attention. Issue #1315 is closed, so reconcile its fix with the implementation base before changing this behavior. |
| The waiting summary describes direct links, not the whole crew. | `src/waiting.ts:75` builds direct-parent entries and does not distinguish `orchWorker`. | A grandchild needing input need not be visible at the root; an ordinary running fork can appear as delegated work. This becomes more important when children collapse. |
| Repeated metadata dominates small rows. | Project line, title, provider/branch row, optional waiting rows in `ThreadCard`; the supplied screenshot repeats the same project. | Less room remains for the actual task and next action. |

The data already distinguishes workers through `orchWorker`, and `crewRootOf` walks the real crew relationship. Use those semantics. Do not create a second persisted family graph to solve a display problem.

## Recommended thread model

**Sidebar: one primary row per independent task.** Keep the existing flat task list and static creation order. Project grouping remains an option. A root row carries a task title, project identity when useful, and one compact summary such as `4 workers · 1 needs you · 1 ready`.

**Workers: one disclosure per task.** Default to collapsed for unrelated tasks. Opening a crew reveals short task-oriented rows, approximately 32–36px high on desktop, without repeating the project. Keep only one visual indentation level; show the actual immediate parent in the worker detail when needed. Preserve the underlying ancestry.

**Independent forks: independent rows.** A manual fork is a new direction, with a small provenance link to its origin. Put explicit compare/alternative runs in an alternatives group when that relationship is known. Do not guess that every `handoffFrom` record is a worker or experiment.

**Provider subagents: activity within their owning thread.** Preserve their descriptions and status, but do not invent navigable thread rows where no thread exists.

**Names: the assigned job.** Prefer a supplied worker/task title such as “Review keyboard navigation.” Let worker creation accept a short title, with a bounded first-line prompt fallback. Centralize generated-name handling at the shared fork creation boundary, including browser dev parity. For old generated names, derive a cleaner display label conservatively; do not silently rewrite user-authored titles or run a model just to rename every record.

**Root status: the next human action.** Use clear labels such as `Needs input`, `Running`, `Ready for review`, `Stopped`, `Failed`, and `Integrated`. Keep process state distinct from integration state: a worker finishing does not prove that its changes are verified or landed. Use existing verification and integration evidence. Stopped and failed work must not look like healthy waiting.

**History: folded, recoverable, explicit.** Integrated/landed workers can move into a `Completed (n)` disclosure immediately. Ready-but-unreviewed, blocked, failed and stopped work stays in the visible task summary. Folding is presentation only; it must not archive threads, remove worktrees, discard unread state, or bypass integration approval.

Important interaction rules:

- A blocked descendant contributes to the root's needs-input count even when the crew is collapsed. Count actual crew members once and guard missing parents/cycles.
- Selecting a hidden worker reveals its containing task. Search includes workers and shows their task context. Keyboard traversal and multi-select use exactly the rows that are visible.
- Pinned, snoozed, manually settled and archived children retain their explicit lifecycle semantics. A missing/archived parent must not strand active work.
- Remember disclosure choices. New workers do not steal selection or expand every task.
- Strengthen the existing dismissible “Forked from” banner into persistent task/worker breadcrumbs for workers. Solenta already has parent navigation; improve its prominence.

## Broader app recommendations

| Priority | Area | Recommendation |
| --- | --- | --- |
| P1 | Worker review | Put a `Workers (n)` entry beside the thread title that opens the existing Team and CrewIntegration view. Show task, provider, current state, change summary, verification and merge destination together. Reuse the existing review/integration controls. |
| P1 | Transcript | Retain existing tool groups and Summary/Verbose modes. Make routine worker dispatch/completion notices a compact expandable activity group. Leave questions, failures, permission requests and actionable results visible. Finished turns should read as outcome, changes and verification, with details on demand. |
| P1 | Selection and text | Make titles the first visual line. Use a quiet selected-row fill with a small edge marker, and consistent secondary text. Avoid fading the entire unselected working card to 70% opacity; mute metadata locally so task titles remain legible. |
| P1 | Main navigation | The app has ten top-level view types and five inspector tabs. Keep the frequent destinations visibly labeled: Threads, Planboard and Review. Put Activity/Kanban and operational views in a predictable Views menu and the existing command palette. Retain scope and return navigation. |
| P2 | Composer | Keep model, mode, permissions and send behavior visible. Group occasional workflow, best-of-N and advanced controls behind one options entry. Clearly retain the Queue versus Steer choice during a run; this is meaningful behavior, not metadata. |
| P2 | Inspector | Make the right panel contextual: worker/team details for orchestration; changes for review; project context for memory/skills. Keep its existing collapsed-by-default preference. Avoid putting another permanent dashboard beside the transcript. |
| P2 | Width and responsiveness | Prioritize existing [#358](https://github.com/currentbits/solenta/issues/358): resizable sidebar. Preserve useful titles at narrow widths, move optional metadata into detail, and use the existing narrow-screen drawer behavior. |
| P2 | Visual consistency | Retain the app's theme tokens and typography initially. Reduce competing borders, provider marks and colored status decorations. Use one selection accent plus semantic warning/error/success colors. The website's paper/yellow palette is a separate established system, not a mandate to recolor the desktop app. |

Useful capabilities already exist: command palette, saved filters, stable sidebar ordering, parent navigation, collapsible inspector, Team, CrewIntegration, per-turn diffs, grouped tools and transcript view modes. Improving access to these is more valuable than duplicating them.

## Motion review and proposal

| Before | After | Why |
| --- | --- | --- |
| Full-size child rows remain permanently visible. | Opening a worker group moves affected rows over about 150–180ms; a small chevron rotates. Keyboard activation may snap. | Explain where child work belongs without slowing navigation. |
| Working, waiting, delegating and unread-done can all pulse indefinitely (`Sidebar.tsx:612`, `Sidebar.module.css:687`). | Use static symbols/text for idle waiting and completion; reserve any activity motion for actual running work. Briefly transition a changed status once. | A finished worker should stop asking for visual attention. |
| A 150ms AutoAnimate is already attached to the list (`Sidebar.tsx:144`). | Reuse it first. Gate initial hydration, search/filter replacement and large batches; verify grouped children are in the animated container. | Preserve object continuity without animating a complete refresh. Do not add another motion library. |
| New transcript entries already move 6px and fade for 180ms (`ThreadView.module.css:1773`). | Preserve the append-only gate. Optionally reduce travel to 4px; never animate individual tokens or replay history on selection. | Existing behavior already captures much of the desired T3 feel. |
| Completed work retains the same presentation as active work. | Once integration is confirmed, update the completed count and move the row into its fold in one short transition. Keep selection stable. | Motion explains a real lifecycle event. |
| Several motion surfaces have separate local rules. | Use a small shared duration/easing vocabulary; keep navigation immediate and motion interruptible. Audit reduced-motion handling across the whole screen. | Cohesion is more useful than extra effects. |

Suggested budgets (design proposals, not measured performance):

- Sidebar lifecycle movement/disclosure: 150–180ms, transform/opacity, `cubic-bezier(0.23, 1, 0.32, 1)`.
- Worker state change: approximately 120ms; no recurring completion pulse.
- Contextual panel opening: 180–220ms, small translation, no overshoot.
- Existing message append: retain 180ms and stable item keys.
- Thread switch, keyboard navigation, streamed tokens and initial history: immediate.
- Reduced motion: no displacement, bounce, shimmer or recurring pulse. Status labels and focus remain fully usable.

**Verdict:** block adding more perpetual motion before fixing grouping. Keep the existing append-only message entrance. Review real frames under concurrent worker streaming before approving list or panel motion for release. This audit did not measure frame time.

## What to borrow from T3 Code and Orca

T3 Code's current [sidebar motion implementation](https://github.com/pingdotgg/t3code/blob/e67abcf798f8c4d8458755e3b4dde02c2c1f628b/apps/web/src/components/Sidebar.motion.ts) uses 150ms transitions, carries movement forward when interrupted, honors reduced motion and skips fades for updates affecting more than 40 rows. Borrow the short duration, continuity and bulk guard, not the whole implementation. Solenta already has AutoAnimate.

T3's [timeline](https://github.com/pingdotgg/t3code/blob/e67abcf798f8c4d8458755e3b4dde02c2c1f628b/apps/web/src/components/chat/MessagesTimeline.tsx) uses compact tool-group rows and restrained hover/disclosure transitions. Solenta already adopted grouping; the next gain is making the worker activity equally coherent.

Orca's [orchestration documentation](https://github.com/stablyai/orca/blob/122b8c25d7c16f76e395bf9a65887d7c4bc5003b/docs/site/content/docs/cli/orchestration.mdx) distinguishes a task from its dispatch attempts, gives tasks short titles, and retains inspectable output after worker release. Borrow that product distinction. Solenta can express most of it using its existing worker links, tasks and integration receipts; it does not need Orca's runtime architecture. Here “Orca” means [Stably's Orca](https://github.com/stablyai/orca).

The proposed collapsible task family is a Solenta recommendation informed by those patterns, not a claim that either product implements this exact design.

## Implementation sequence and acceptance

1. **Fix identity and hierarchy.** Bounded generated names, worker/fork classification, crew-root summary, collapsed worker families and selected/search reveal. Start with `services.js`, `sidebarGroups.ts`, `waiting.ts` and Sidebar; inspect all callers before edits. Acceptance: one task with 20 workers and several grandchildren stays one understandable row when collapsed; hidden input requests remain discoverable; plain forks remain independent.
2. **Bring review into the task.** Expose existing Team/CrewIntegration from the header, strengthen breadcrumbs, fold integrated history, and compact routine orchestration notices. Acceptance: open a worker, inspect changes/verification, return to the task and review remaining work without hunting through separate views. No automatic merging or destructive cleanup.
3. **Polish motion and density.** Short lifecycle transitions, quieter status indicators, tighter metadata and consistent selection. Acceptance: rapid open/close reverses cleanly; keyboard and reduced-motion flows remain immediate; no reanimation on thread switches or history reveal; worker streaming does not reorder tasks or steal scroll.
4. **Simplify the wider app.** Labeled primary navigation, contextual inspector, composer options and sidebar resizing. Validate against real multi-project use before hiding secondary controls.

Focused regression checks should cover nested workers, missing/cyclic parents, manual forks, pinned/snoozed/settled children, selected hidden rows, search context, ready versus integrated status, and reduced motion. Add checks to the existing test suites rather than creating a parallel test framework. Verify the existing closed #1315 behavior on the chosen implementation base; the open #183 already covers stopped-worker ambiguity, so update it rather than file a duplicate.

The first phase offers the largest improvement. A font swap, new animation dependency, graph view or new dashboard would not solve the problem shown in the screenshot.

## Concept validation

`work/solenta-thread-concept.html` is an interactive design concept with illustrative data, not a connected Solenta interface. `node work/check-thread-concept.cjs` passes: worker disclosure, parent/worker navigation, completion without integration, mouse motion, immediate keyboard activation, reduced motion and ARIA target checks. Its standalone preview was generated successfully. Visual browser inspection was not completed; the available test browsers were headless and the Solenta application was denied. No production application code was changed.
