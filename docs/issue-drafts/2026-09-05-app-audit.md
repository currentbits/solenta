## Separate issue bodies

### 1. Unsent composer drafts disappear when switching threads in the real App

**Priority: P1.** Reproduced/reviewed at commit `6c7a6fbe` on 2026-09-05.

Switching from thread A to B and back silently loses A's unsent prompt.

### Reproduction
1. Open a thread in the app and type a prompt without sending it.
2. Select another thread in the sidebar.
3. Return to the first thread.
4. The composer is empty.

Confirmed by mounting the real App with createFakeCoder and navigating A → B → A. This is not merely a Composer-only test.

### Cause
App gates visibleDetail to null while the new selection's detail is fetched. ThreadView's no-detail branch omits Composer, unmounting it. Composer keeps draftsRef, attachmentsByThread and pasteCardsByThread in component-local memory, so the draft map is discarded. Existing test/composer.test.tsx:475 assumes one continuously mounted Composer and misses the real lifecycle. Related to closed #12, but the current symptom is lost drafts rather than drafts leaking between threads.

### Acceptance
- An unsent prompt survives A → B → A through the real App, including uncached detail loads.
- Pending attachments and paste cards remain associated with their source thread.
- Switching to another main view and back preserves unsent input too.
- Preserve the stale-detail protection: never show A's transcript under B's selection.
- Add an App-level regression check; a Composer-only threadId swap is insufficient.

Source: [src/App.tsx#L933](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/App.tsx#L933).

Requested disposition: separate Planboard issue, `plan:todo`. Scope is the concrete defect above.

### 2. Failed mid-run queue saves clear the composer and lose the follow-up

**Priority: P1.** Reproduced/reviewed at commit `6c7a6fbe` on 2026-09-05.

A follow-up typed during a working run disappears when threads.setQueued rejects, even though it was never saved.

### Reproduction
1. Mount App on a working thread.
2. Make api.threads.setQueued reject, e.g. a disconnected bridge or rejected persistence request.
3. Type a follow-up and click Send.
4. The error is shown, but the composer is blank and no queued copy exists.

Confirmed with the real App/useCoder/Composer and a rejecting fakeCoder method.

### Cause
The busy branch of useCoder.startRun catches the queue write error and returns normally. Composer.runAction interprets fulfilled onSend as success and clears the draft, attachments and paste cards. The idle start and /btw branches already rethrow, so the inconsistency is localized.

### Acceptance
- A failed queue write leaves the prompt and associated input intact and retryable.
- Successful queueing clears the composer exactly once.
- Show the failure without claiming that the prompt was queued.
- Cover the entire App → useCoder → Composer path with a rejected setQueued call.

Source: [src/useCoder.ts#L1467](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/useCoder.ts#L1467).

Requested disposition: separate Planboard issue, `plan:todo`. Scope is the concrete defect above.

### 3. Failed queue cancellation hides work that is still scheduled on the host

**Priority: P1.** Reproduced/reviewed at commit `6c7a6fbe` on 2026-09-05.

Cancel removes a queued follow-up from the UI before the host confirms cancellation. If the call fails, the queue stays hidden while the host still holds work that can run at turn end.

### Reproduction
1. Open a working thread with a persisted queued follow-up.
2. Make api.threads.setQueued({prompt:null}) reject.
3. Click the queued follow-up's Cancel action.
4. The queue strip disappears.
5. Read the thread from the host/fakeCoder: its queued prompt is unchanged.

Confirmed in the mounted App with the host queue and rendered queue checked separately.

### Cause
useCoder.cancelQueued optimistically replaces queued with null. The catch only sets the global run error and never restores or reloads the queue.

### Acceptance
- Keep the queue visible until cancellation is confirmed, or reconcile it on failure.
- Clearly indicate a failed cancellation and offer a retry.
- Do not overwrite a newer queue update when reconciling.
- Verify that UI and host agree after both success and failure; a failed cancellation must not look successful.

Source: [src/useCoder.ts#L830](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/useCoder.ts#L830).

Requested disposition: separate Planboard issue, `plan:todo`. Scope is the concrete defect above.

### 4. Manual run preflight failures permanently discard an existing queued prompt

**Priority: P1.** Reproduced/reviewed at commit `6c7a6fbe` on 2026-09-05.

Starting a new user turn consumes an existing queue before validating whether the run can start. If the daily budget gate rejects the run, the old queued instructions are lost, including on disk.

### Reproduction
Using a real Store and createRunner:
1. Create an idle thread and services.setQueued with an existing prompt.
2. Set dailyBudgetUsd to 1 and recordSpend(1).
3. Call runner.startRun with a new user prompt.
4. The call rejects with Daily budget reached.
5. thread.queued is null, no transcript messages were appended, and reloading the saved Store still yields queued:null.

This was reproduced without launching a provider or touching a real user store.

### Cause
The ordinary startRun path calls services.takeQueued and folds the taken text into the local prompt before assertUnderDailyBudget, provider availability and worktree preflight. Unlike drainQueued, this path has no restoration on rejection.

### Acceptance
- A run that fails before accepting the prompt preserves all previously queued text and attachments.
- Cover budget rejection, missing provider and worktree setup failure.
- Once a run is accepted, queued content is delivered exactly once.
- Restoration must not overwrite follow-ups queued in the meantime.
- Include a real Store/runner regression test and verify persistence after reload.

Source: [electron/runner.js#L7570](https://github.com/currentbits/solenta/blob/6c7a6fbe/electron/runner.js#L7570).

Requested disposition: separate Planboard issue, `plan:todo`. Scope is the concrete defect above.

### 5. Retry duplicates queued instructions when clearing the old queue fails

**Priority: P1.** Reproduced/reviewed at commit `6c7a6fbe` on 2026-09-05.

Retry can duplicate a queued prompt without starting a run.

### Reproduction
1. Open an idle thread with queued.prompt = "Retry this once" and a delivery error.
2. Make the clear call to threads.setQueued({prompt:null}) reject.
3. Allow subsequent non-null setQueued calls to succeed.
4. Click Retry.
5. runs.start was never called, but the host queue is now "Retry this once\n\nRetry this once".

Confirmed in the real App with fakeCoder's normal append behavior.

### Cause
useCoder.retryQueued wraps both clear and start in one try/catch. The catch always re-enqueues the old payload, even when the clear itself failed and the payload never left the host. services.setQueued appends by default. The same mistake can duplicate attachments. The local overlay still uses the original pending object, masking the host duplication.

### Acceptance
- A failed clear leaves exactly one copy of the old prompt and attachments.
- Only compensate for a removal that actually succeeded.
- A rejected start after a successful clear restores the original payload exactly once.
- Preserve newer concurrently queued content.
- Assert host queue contents, not just the rendered error.

Source: [src/useCoder.ts#L848](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/useCoder.ts#L848).

Requested disposition: separate Planboard issue, `plan:todo`. Scope is the concrete defect above.

### 6. Failed queued-message edits close the editor and discard the revised text

**Priority: P2.** Reproduced/reviewed at commit `6c7a6fbe` on 2026-09-05.

Saving an edited queued follow-up discards the edited text when persistence fails.

### Reproduction
1. Open a thread with queued text "Original queued text".
2. Click Edit and replace it with different instructions.
3. Make threads.setQueued reject, then click Save.
4. The editor closes and the old queued text remains.
5. Reopen Edit: only the original text is available; the revised draft has been discarded.

Confirmed through the real App with a rejecting queue write.

### Cause
ThreadView.saveQueuedEdit closes the editor synchronously, before the write. onEditQueued is typed as returning void, and useCoder.editQueued starts an unawaited promise chain. Its catch shows a run error but cannot retain the editable draft as a failed save.

### Acceptance
- Keep the revised text editable until the save succeeds.
- On failure, retain the revised draft with a visible retryable error.
- Prevent repeated saves while one write is pending.
- Preserve ordered queued items and attachments.
- Add a mounted App regression that reopens or retries after a rejected write.

Source: [src/components/ThreadView.tsx#L4762](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/components/ThreadView.tsx#L4762).

Requested disposition: separate Planboard issue, `plan:todo`. Scope is the concrete defect above.

### 7. Thread search reports backend failures as No threads match

**Priority: P2.** Reproduced/reviewed at commit `6c7a6fbe` on 2026-09-05.

When the thread search API rejects, the sidebar reports a valid empty result instead of a failure. Users can conclude that their work is missing.

### Reproduction
1. Make searchThreads reject with an error.
2. Enter a query of at least two characters.
3. Wait for the debounce.
4. The sidebar shows "No threads match" without a search failure or Retry.

Confirmed by mounting Sidebar with a rejecting searchThreads function.

### Cause
runSearch catches every rejection and sets searchResults to an empty array. The empty-result rendering cannot distinguish a failed request from a successful search with zero matches.

### Acceptance
- Distinguish loading, successful empty results and search failures.
- Provide an inline failure message and Retry.
- Clear obsolete errors when the query changes.
- Preserve generation checks so stale requests cannot replace newer results.
- Test a rejected request and a subsequent successful retry.

Source: [src/components/Sidebar.tsx#L1586](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/components/Sidebar.tsx#L1586).

Requested disposition: separate Planboard issue, `plan:todo`. Scope is the concrete defect above.

### 8. Settings and onboarding dialogs do not manage keyboard focus

**Priority: P2.** Reproduced/reviewed at commit `6c7a6fbe` on 2026-09-05.

Settings and onboarding declare aria-modal=true but do not implement modal keyboard focus behavior. Opening Settings leaves keyboard focus on the background control.

### Reproduction
1. Focus a button outside Settings.
2. Open Settings.
3. Observe that document.activeElement is still the background button.
4. The dialog is a div with role=dialog; the background is not made inert by opening Settings.

Initial-focus failure was reproduced in the mounted Settings component. Source inspection also found no initial focus, containment or focus restoration in OnboardingModal. Real browser Tab traversal remains to be checked because browser access was unavailable during the audit.

### Cause
These components use role/aria attributes and useEscapeClose, which handles Escape only. The App's inert attributes cover narrow-layout drawers, not these modal dialogs.

### Acceptance
- Move focus into each dialog on open.
- Keep keyboard navigation within the active modal.
- Restore focus to a surviving opener when closing.
- Correctly handle nested flows such as onboarding opening Add Project.
- Prefer existing/native behavior over a new dependency.
- Verify actual activeElement and real browser Tab/Shift+Tab behavior; markup assertions alone are insufficient.

Source: [src/components/SettingsModal.tsx#L809](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/components/SettingsModal.tsx#L809).

Requested disposition: separate Planboard issue, `plan:todo`. Scope is the concrete defect above.

### 9. Opening an uncached thread displays Select a thread while it is loading

**Priority: P2.** Reproduced/reviewed at commit `6c7a6fbe` on 2026-09-05.

After the user selects a thread, the main pane can instruct them to select a thread while the requested detail is still loading.

### Reproduction
1. Mount App with threads A and B.
2. Select A, then defer api.threads.get(B).
3. Click B in the sidebar.
4. B's request is in flight, but the main pane says "Select a thread".

Confirmed through the real App with a deferred thread-detail request.

### Cause
App intentionally gates visibleDetail to null when detail.thread.id differs from selectedThreadId. ThreadView sees only null plus no error and renders the no-selection empty state. It receives no explicit loading state to distinguish these situations.

### Acceptance
- Show a loading state for an uncached selected thread.
- Reserve "Select a thread" for no selection.
- Keep cached-thread rendering and the stale-detail safety check.
- Preserve the existing failed-load Retry UI.
- Check a deferred request, a rejection, and rapid A/B selection.
- Coordinate with the draft-preservation fix: loading must not destroy unsent composer state.

Source: [src/App.tsx#L933](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/App.tsx#L933).

Requested disposition: separate Planboard issue, `plan:todo`. Scope is the concrete defect above.
