## 1. Reconnect coalescing drops repeated writes and acknowledges changes the host never applied

**Priority: P1.** Reproduced at commit `6c7a6fbe` on 2026-09-05.

In the web client, queued writes are deduplicated like polling reads. An offline true → false → true settings sequence reaches the host as only true → false, while all three callers resolve successfully.

### Reproduction
1. Authenticate createWireCoder against a fake socket, then disconnect.
2. Invoke settings.set({notifications:true}), settings.set({notifications:false}), settings.set({notifications:true}) while offline.
3. Reconnect and acknowledge the outgoing requests.
4. Only two settings:set requests were sent; the final host value is false. The three promises return true, false, true.

### Cause
src/wireClient.ts:65 flushQueue groups every request by JSON.stringify([channel,args]), including mutations. The last true write borrows the first write's reply despite an intervening false write. This affects mutation semantics, not just visual refresh.

### Acceptance
- Preserve every queued mutation and its order, including repeated arguments separated by another write.
- Restrict coalescing to explicitly safe read requests; retain bounded queues/timeouts.
- Cover true/false/true writes and repeated safe polling in one transport regression test.

Related closed #130 introduced reconnect coalescing to reduce polling stampedes. This is a distinct correctness defect in that behavior.
Source: [wireClient.ts](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/wireClient.ts#L65).

## 2. Web reconnect refreshes the sidebar but leaves the open transcript stale after a missed final update

**Priority: P1.** Reproduced at commit `6c7a6fbe` on 2026-09-05.

If a run finishes while the web connection is down, reconnect can show the thread as done in the sidebar while its open transcript still says working and omits the final reply.

### Reproduction
1. Open a working thread through the web bridge.
2. Disconnect while the run completes on the host; miss its final thread:updated push.
3. Reconnect without sending another prompt.
4. threads:list resync updates the sidebar, but the selected detail is not fetched again.

Evidence uses real useCoder with a mounted hook and fake host: initialize working detail with no messages, change host detail to done with a final reply, then emit the threads:changed event generated by wireClient's reconnect path. The list becomes done, detail stays working/empty, and threads.get is called zero times after the refresh. Transport source confirms auth-ok resync requests only threads:list.

### Cause
src/wireClient.ts:137 resyncThreads emits threads:changed. src/useCoder.ts:1071 updates list/projects only. Sequence-gap recovery requires a later thread:updated push, which need not arrive after the run has ended.

### Acceptance
- Resync the selected detail on reconnect, including messages and pending interaction state.
- Retain thread-selection/stale-response guards.
- Test a lost final push with no subsequent activity: sidebar and transcript must converge.

Distinct from #83 (detail during selection changes) and #233/#620 (test timer flake).
Sources: [wireClient.ts](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/wireClient.ts#L137), [useCoder.ts](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/useCoder.ts#L1071).

## 3. Opening Settings before its data loads can silently remove existing spending caps

**Priority: P1.** Reproduced at commit `6c7a6fbe` on 2026-09-05.

Opening Settings before the asynchronous settings fetch completes initializes empty drafts. When saved settings arrive, the modal ignores them. Editing an unrelated numeric preference then sends null for existing spending caps and auto-settle.

### Reproduction
1. Mount SettingsModal open with settings=null, representing the initial useCoder boot state.
2. Deliver saved settings: dailyBudgetUsd=5, orchestrationBudgetUsd=2, autoSettleAfterDays=3, prDiffCapLines=400.
3. Change PR size cap to 500 and press Enter.
4. onSaveSettings receives {prDiffCapLines:500,dailyBudgetUsd:null,orchestrationBudgetUsd:null,autoSettleAfterDays:null}.

Confirmed with the real mounted SettingsModal. App exposes Settings while useCoder's settings state is initially null and passes the later value through.

### Cause
SettingsModal's initialization effect sets wasOpen on the first open render, then skips subsequent settings updates. save() always submits all four numeric drafts, even if the user edited only one.

### Acceptance
- Handle late initial settings without clearing stored preferences.
- Preserve untouched budgets/settle settings when saving another preference.
- Avoid overwriting user edits with subsequent refreshes.
- Add the null → loaded while open regression case.

Sources: [SettingsModal.tsx initialization](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/components/SettingsModal.tsx#L336), [save](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/components/SettingsModal.tsx#L412), [App wiring](https://github.com/currentbits/solenta/blob/6c7a6fbe/src/App.tsx#L1714).

## 4. Weekly automations change weekday when a missed run is caught up

**Priority: P2.** Reproduced at commit `6c7a6fbe` on 2026-09-05.

A weekly automation scheduled for Monday 09:00 permanently moves to Tuesday if the app catches up that missed run on Tuesday.

### Reproduction
1. Create an enabled weekly automation with hour=9 and nextRunAt=Monday 2026-06-08 09:00 local time.
2. Tick the real scheduler with its clock at Tuesday 2026-06-09 10:00.
3. It runs the overdue job once, then saves nextRunAt=Tuesday 2026-06-16 09:00.
4. Expected: the next regular Monday slot, 2026-06-15 09:00.

Confirmed using real Store, services and startScheduler with an injected clock and a fake runner.

### Cause
runAutomation derives nextRunAt from nextFire(preset,hour,now). Weekly nextFire uses the actual execution day's weekday; it does not retain the prior scheduled weekday. Manual runNow uses the same scheduling path and can also move the weekday (source-traced).

### Acceptance
- Preserve the weekly schedule's weekday across sleep/offline catch-up and manual execution.
- Skip missed slots without replaying a backlog.
- Preserve local wall-clock hour across daylight-saving transitions.
- Add a Monday-due/Tuesday-catch-up regression check.

This is schedule correctness, separate from the automation failure circuit breaker in #160.
Source: [automations.js](https://github.com/currentbits/solenta/blob/6c7a6fbe/electron/automations.js#L127).

## 5. Automation retention permanently deletes unfinished threads waiting for quota

**Priority: P1.** Reproduced at commit `6c7a6fbe` on 2026-09-05.

The keep-last-20 automation cleanup treats quota-wait as disposable history. A paused run can lose both its thread and transcript before its scheduled quota reset.

### Reproduction
1. Create an automation and an old unpinned thread without a worktree, with status=quota-wait and quotaWaitUntil a week in the future.
2. Give it a user prompt and unfinished transcript.
3. Create 20 newer completed threads for the same automation.
4. Fire the automation through real runAutomation.
5. The paused thread is gone (getThread returns null) and getMessages returns [].

Confirmed with a real temporary Store and services, plus a fake successful runner. This models a long quota wait while newer automation attempts accumulate.

### Cause
pruneAutomationThreads only protects status=working, worktreePath and pinnedAt. It calls services.purgeThread on quota-wait entries outside the count cap. fireQuotaWake later returns immediately if the thread no longer exists.

### Acceptance
- Preserve quota-wait threads and their messages until the run is resolved or explicitly discarded.
- Review other nonterminal/awaiting-input states against the same retention predicate.
- Continue pruning eligible completed history and protecting pinned/worktree/working threads.
- Add a real-store quota-wait retention check.

Related closed #134 added automation retention; this is unintended deletion of unfinished work in that retention path. #462 implements the quota-resume workflow.
Sources: [retention](https://github.com/currentbits/solenta/blob/6c7a6fbe/electron/automations.js#L101), [quota wake](https://github.com/currentbits/solenta/blob/6c7a6fbe/electron/runner.js#L2782).

## 6. Appending to a thread with a corrupt message shard destroys recoverable transcript bytes

**Priority: P1.** Reproduced at commit `6c7a6fbe` on 2026-09-05.

A corrupt per-thread message shard is treated as an empty transcript. Continuing that thread replaces the damaged file with only the new message, without preserving its original bytes.

### Reproduction
1. Save a thread with an existing message to a real temporary Store.
2. Remove only the closing ] from its messages/<threadId>.json shard.
3. Reload Store and read the thread's messages: the result is [].
4. Append a new user message and call saveNow().
5. The shard now contains only the new message. Its old recoverable text is gone, and the messages directory has no quarantine copy.

This uses injected file corruption to test recovery; it does not claim that normal writes were observed corrupting a live store.

### Cause
_hydrateMessages catches JSON.parse failures, caches [], and forgets the parse failure. appendMessage then marks that empty/new array dirty, allowing the next flush to overwrite the source shard. The existing corrupt-shard test only performs an unrelated envelope save, so it misses the subsequent append.

### Acceptance
- Distinguish missing/empty transcript data from unreadable or malformed data.
- Preserve original bad bytes before any replacement; expose a useful recovery/error state.
- Cover corrupt read followed by append and save, while preserving sibling shards.
- Do not silently turn read failure into successful destructive persistence.

Related closed #133 protects the main store envelope; these per-thread shards follow a different recovery path added by #225.
Sources: [hydration](https://github.com/currentbits/solenta/blob/6c7a6fbe/electron/store.js#L1862), [existing test](https://github.com/currentbits/solenta/blob/6c7a6fbe/electron/test/store.test.js#L2144).
