# Renderer performance on real data (PM2, #1475)

Measured 2026-10-05 on `main` @ `a665aa32`, production build (`CODER_PROD=1`, `dist/`), Electron 35.7.5, M-series Mac with a 120 Hz display. The data was an APFS clone of the live data dir: 2,097 threads, 958 live, 14 projects, 788 MB of message shards. The app was driven over CDP with Playwright. Timings come from in-page `performance.now()` plus `requestAnimationFrame`, Long Animation Frame (LoAF) entries, CDP CPU profiles (mapped to source through a sourcemap build of the same bundle hash), `HeapProfiler`/`Memory.getDOMCounters`, and `ps` RSS.

The streaming runs used the `generic` provider with `CODER_AGENT_CMD` set to a local script. It streams markdown in 20 ms chunks, ~45 k chars per 25 s run, through the same 250 ms throttled `thread:updated` push path real providers use. No real agents ran.

### Which launch each number comes from

- **Unsafe launch (19:37, the one that touched real repos; see the last section): no measurements in this report.** That session produced only an orientation DOM probe and the localStorage key listing. The single figure taken from it is the **1,667 stale `coder.paneLayout.*` keys** in finding #8. The later guarded session's totals (1,684 keys, 3.14 M chars) agree with it.
- **Guarded launches (19:40 onward): every other number.** That covers cold starts, reloads, switches, sidebar, streaming, typing, memory and soak. These launches had:
  - real-repo git blocked by a shim, which wasn't bypassed: 1,133 denied, 164 allowed, all inside `/tmp/pm2-scratch`;
  - `HOME`/`SHELL` sandboxed;
  - the clone's worktrees emptied and its `worktreePath`s rewritten into the clone;
  - its own memory and orch servers;
  - runs limited to a local fake-agent script.

  This is weaker than PM1's later recipe (memory `solenta-cloned-data-dir-launch`): no `env -i`, no scheduler stubs, no fs-write guard. With git blocked and the worktree paths rewritten, the boot sweeps and schedulers had nothing real to act on in the guarded sessions. Any repeat should use PM1's recipe.

## What is fine

- **Sidebar.** By default only 4–16 rows are mounted: project groups and the settled shelf are collapsed, and settled rows page in 25 at a time. Paging all the way to **966 rows (9,051 sidebar nodes)** never produced a frame over 50 ms; each page took 8–17 ms. Wheel-scrolling the 966-row list dropped 21% of 120 Hz frames, but the worst gap was 25 ms and there were no long frames. Virtualization isn't needed at this size.
- **Streaming into a thread that is not open** costs nothing measurable: 0 LoAF, 0.1% dropped frames, typing latency unchanged.
- **Typing while idle:** keydown → next frame median 5 ms, max 10–14 ms.
- **Small-thread switches:** 32–46 ms with no long frames.
- **No leaks on switching.** After opening the 10 largest live threads in a row and switching back, DOM nodes returned to baseline (4,037 → 4,045) and listeners to 546. JS heap plateaued at 29–33 MB, which is the bounded 8-entry/8 MB `threadDetailCache`. Renderer RSS stayed at 235–301 MB.
- **Boot-snapshot and detail-cache writes:** ~11 ms and <1 ms. They are debounced and not a problem.
- **Transcript windowing (#564)** does work on open: the 1,055-message threads mount 2.0–3.9 k elements, not all of them. The problem is only that the window grows afterwards (#2).

| after stream | 0 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|---|
| heap MB | 39.5 | 50.2 | 58.8 | 63.2 | 67.5 | 73.9 | 78.6 |

| renderer RSS MB | 275 | 364 | 396 | 406 | 423 | 549 | 579 |

After switching to a small thread: 32.2 MB heap, 4.3 k nodes, RSS 444 → 371 MB after 15 s. Reopening the big thread mounted 57 k nodes again, because the 120-entry window now held the six 45 KB answers. A `vmmap` of the renderer at that point showed a 326 MB physical footprint (peak 823 MB), mostly Chromium allocator regions (memory tags 253/255: ~480 MB resident, ~290 MB dirty). The malloc zone held only 21 MB. So the RSS is DOM, layout and JS heap, not native leaks.

The live renderer (pid 67639) was at **490 MB after 25 h** of uptime, read with `ps` only and not attached to. That fits finding #2: a long-open, active thread accumulates DOM. Two other explanations are possible and weren't checked, since attaching to the live app was off limits: images in the transcript, and an open terminal.

## Method notes and caveats

- 120 Hz panel: "dropped frames" are relative to 8.33 ms frames. At 60 Hz the same work drops roughly half as many frames.
- I didn't build a React Profiler bundle. CPU profiles mapped through a sourcemap build of the identical bundle (`index-CY9ilrU5.js`) attributed every long frame, which was enough to name the components.
- `performance.memory` is quantized in Electron (it read 50.4 MB flat throughout), so memory comes from CDP `Runtime.getHeapUsage` after `HeapProfiler.collectGarbage`.
- The synthetic stream is pure markdown text. Real agent turns add tool cards and work-log rows, which hit #1 harder (more tool inputs to `JSON.parse`) and #4 less.
- Scripts were scratch files under `/tmp/pm2` (`switch.js`, `stream.js`, `sidebar.js`, `mem.js`, `soak.js`, `instr.js`, `map.js`) and were not committed.

## Hazard: running the app against a cloned data dir

The first launch against the clone changed real repositories. Anyone repeating this needs to know why:

1. **The boot orphan sweep follows the clone's worktree pointers.** `electron/worktrees-gc.js` `sweepOrphanWorktrees` runs 15 s after boot. It treats every `<clone>/worktrees/*` dir as an orphan, because the store's `worktreePath` values point at the live dir. Each clone worktree's `.git` file points into the real repo's `.git/worktrees/<id>`, and that HEAD and index are shared with the live worktree. For three dirty archived worktrees (2 × huskyscout, 1 × appfeedback), the sweep ran `git switch -c recovered/<id>`, `add -A` and `commit`, which moved the live worktrees' HEAD. I reversed it: `git symbolic-ref HEAD` back to the original branch, then a mixed reset. Every file was verified against the recovered commit, and the `recovered/*` branches were deleted. No work was lost.
2. **A PATH shim alone does not isolate git.** `electron/pathEnv.js` prepends the login shell's PATH, so `/usr/bin/git` wins. Set `SHELL=/nonexistent` as well.
3. **The memory server adopts the live one** through `<clone>/memory-server.json` and rewrites `~/.grok/config.toml`. Delete the server-port JSONs and set a throwaway `HOME`.
4. **Playwright's `browser.close()` quits Electron** on a `connectOverCDP` connection. Disconnect with `process.exit` instead.

Safe recipe used for every measurement above:
- empty `<clone>/worktrees`;
- rewrite `worktreePath` and the scratch project path in the clone's `coder-store.json` into the clone;
- delete `memory-server.json` and `orch-server.json`;
- launch with `HOME=/tmp/…-home SHELL=/nonexistent PATH=<shim>:/usr/bin:/bin`;
- use a `git` shim that only allows a scratch repo (1,133 calls denied, 164 allowed, all in `/tmp/pm2-scratch`);
- set `CODER_AGENT_CMD=<local script>` (or `CODER_SIMULATE=1`).

The sweep is arguably a product bug for any launch with a non-default `--user-data-dir`. Removing a "not referenced" worktree whose common dir is outside `worktreeBase` deserves a guard.
