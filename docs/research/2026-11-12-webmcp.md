# Local Browser WebMCP adoption

Implemented 2026-11-12. Tracking: [#2003](https://github.com/currentbits/solenta/issues/2003).

## Sources and scope

Synara [#808](https://github.com/Emanuele-web04/synara/pull/808) and its
[current guest bridge](https://github.com/Emanuele-web04/synara/blob/83e0533b23099908ee14e4fecacd5ed702f4d453/apps/desktop/src/browserWebMcp/guestBridge.ts)
informed the preload compatibility API, on-demand discovery, descriptor fencing,
cancellation and bounds. This is a small independent implementation for Solenta's
existing loopback preview, without Synara's browser runtime or declarative form
emulation. Upstream research remained read-only.

The current [Chrome imperative API documentation](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
(updated October 16, 2026) registers on `document.modelContext`, discovers with
`getTools()`, executes a discovered descriptor with an arguments object, and uses
AbortSignal for unregistering/cancellation. Electron 35's Chromium predates this
native surface, so registration must be available before application scripts.

## Use

Open the thread's Browser pane on a local development page. Through the existing
`preview` tool, call:

```json
{"action":"webmcp_tools","threadId":"…","projectId":"…"}
```

Use a returned `ref` with `webmcp_invoke` and an `arguments` object. Supply an
`invocationId` to address a pending call with `webmcp_cancel`; otherwise Solenta
generates one. Rediscover after cancellation, navigation, reload, registration
changes or another discovery. No page scripts or JavaScript source are accepted
from the agent.

Pages register JavaScript tools with `document.modelContext.registerTool(tool,
{signal})`. The compatibility API also exposes the Navigator registration alias.
Aborting the registration signal unregisters the tool. Callbacks receive an
arguments object and `{signal}`. Only the top-level document is supported.

## Boundaries

- The guest stays sandboxed with context isolation and no Node integration. Its
  caller-supplied preload is replaced with Solenta's fixed preload. No `coder`
  bridge or host methods are exposed to page scripts.
- The host reads main-document response headers and supplies a boolean policy to
  the preload. Compatibility registration requires a secure local document and
  an observed response. On old Chromium, any explicit `tools` Permissions-Policy
  directive disables compatibility, including allow-lists. This conservative
  subset avoids pretending to implement the browser's policy parser. A native
  context, when available, owns its native policy enforcement. Discovery also
  re-checks that host-observed policy, so a page cannot plant its own bridge
  global on a denied document. Same-document navigation (pushState, hash) keeps
  the document's policy; a cross-document navigation start drops it.
- Discovered refs contain a per-document random identifier; the host skips refs
  not prefixed by the reporting document's id and keeps each ref's descriptor in
  the thread's bound session (another thread's pane never sees it). The host also
  checks the bound session and document generation. The guest re-reads the descriptor,
  rejects changes and checks registration identity; `toolchange` invalidates
  retained refs. Main-frame navigation starts invalidate refs and cancel calls.
- Web clients need the existing `preview` action scope to invoke/cancel. Discovery
  uses the existing read scope. The thread MCP surface retains its own-thread and
  same-project checks. Page `readOnlyHint` and `consequentialHint` are untrusted
  metadata and never grant permission.
- Names, descriptions, schemas, errors and results remain untrusted. Results are
  returned under `result`, without interpreting embedded tool requests or images.
  Compact MCP JSON preserves the payload bounds without indentation expansion.
- Each invocation has a five-second deadline, up to eight pending calls per bound
  session. Timeout, cancellation, navigation and page errors return uncertain
  completion; the callback may already have changed state. Never retry a mutation
  automatically. AbortSignal is cooperative and cannot undo completed effects or
  stop a synchronous busy loop.
- At most 128 registrations/tools, 128-byte names, 4 KiB descriptions, 16 KiB
  schemas/arguments, 32 KiB aggregate discovery entries, 64 KiB results, and 20
  JSON nesting levels. Host-side bounds independently reject forged responses.
  Discovery reports omitted native tools as `skipped`.

The compatibility API validates descriptor shape, serializability, object inputs
and resource limits. Before the page sees a call, the host checks arguments
against the discovered schema's top level: `required`, property `type`
(including type unions and `integer`), `enum`, and `additionalProperties: false`.
Rejected calls never ran. Nested values are not schema-checked; callbacks must
still validate application arguments (#2010). No declarative forms, frame traversal, legacy
`provideContext`, automatic tool invocation, or browser engine upgrade is included.
Native Chromium API integration has only fixture coverage on this Electron version.

## Verification

- Focused Node suites cover the bridge, preview lifecycle/Inspect, real MCP
  schema/dispatch and web-client permission enforcement. They run with inherited
  `CODER_*` variables removed and provider CLIs excluded from PATH.
- Renderer channel-contract and BrowserPane tests pass, along with typecheck and
  preload-table synchronization.
- `node node_modules/electron/cli.js scripts/verify-browser-webmcp.js` uses a real
  sandboxed `<webview>` and production guest policy. It verifies registration
  during page load, read and mutation callbacks, registration removal,
  signal cancellation, oversized output refusal, same-URL reload fencing,
  `tools=()` denial and response-policy reset. The page has neither Node `require`
  nor the host `coder` bridge.
- The composited host screenshot `/tmp/solenta-webmcp.png` was inspected and shows
  the page counter at 2. Direct guest capture returned transparent pixels in this
  fixture; the screenshot check uses the composited host window.

No signed packaged build, native WebMCP browser, installed-app upgrade or main-branch
integration was tested. This feature remains local to this worktree branch.
