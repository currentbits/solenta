Shared memory

Your agents remember.

What one thread learns, the next one knows. Solenta injects a local memory server into every agent session automatically, so decisions and gotchas persist across Claude Code, Codex, Kimi, Grok and OpenCode. The tenth session on a project is better informed than the first.

  • Injected automatically. When the local server is healthy, every new session gets it. You do not wire it up per agent.
  • Local, and yours to search. HTTP + MCP, localhost-only, bearer-token gated. The Memory tab reads the same SQLite file the agents write, with full-text and vector search.
  • It compounds. Session ten does not re-learn what session one already ruled out.

Agent teams, not just fan-out

Workers share a crew task list and message each other directly. A shared per-repo code index goes into every dispatched prompt, so a fresh worker starts knowing where things live.

Teach mode

Hints, not solutions, on every provider. Autonomy steps up as reviews pass, and permission modes stay gated to the current rung.

Ask first

Read-only questions about the repo, answered from the code index and shared memory. No worktree, no tools, no spend. Start work when you are ready to change things.

Spec, then dispatch

Requirements, design, tasks, each one gated until you approve. Then Dispatch forks a worker per unblocked checkbox, and Converge fills in what the repo is still missing.

A review itinerary, not a file list

Every agent diff gets a risk-ranked read order: CI and config first, then reuse, the critical path, tests, and the rest. Git is a tab in the thread, not a card in the rail.

Green means verified

A thread only settles green once its verify command exits 0. Guardrails protect the config a worker may not touch, and scan what it brings back for injection and secrets.

Fleet analytics from ground truth

Merge rate, review tax, rework and cost per merged PR, read off git and GitHub, not off what the agents say about themselves.

Orchestration is a sentence, not a config.

Every thread carries tools to drive the other threads. You describe the fan-out in plain language; the agent spawns, supervises and reports back.

  • Fork across providers. The same task on Grok, Kimi and Claude at once, each in its own worktree.
  • Or delegate from the start. An orchestrator thread hands its first prompt to a worker and supervises from there, one setting away from being the default.
  • Async by design. Runs go off in the background; the orchestrator polls and summarizes.
  • Suggested work, one click. Out-of-scope findings land as chips under the transcript, not as a derail.
  • Or pick a fixed pipeline. The Build button runs a known template when the shape is repeatable.

Questions.

Which agents can Solenta run?

Claude Code, Codex, Kimi, Grok and OpenCode. Install the CLIs you want to drive and Solenta finds them on your PATH. Permission modes, model overrides and session resume are per provider.

Does my code leave my machine?

Only inside the prompts your chosen agent CLI sends to its provider, same as running that CLI yourself. Solenta adds nothing on top: memory is a local SQLite file, plans are your own GitHub issues, and there is no Solenta cloud.

Do I pay Solenta for tokens?

No. Bring your own subscription or API key per provider. Solenta never resells tokens and never sits in the billing path.

What does the planboard need?

The GitHub CLI signed in, and a project whose origin is on GitHub. Without those, threads, memory and everything else work exactly the same; the board simply stays off.

Is it free?

Yes. MIT licensed, with releases for macOS, Windows and Linux.

You own the tools.

Solenta is MIT licensed and runs on your machine. It drives the agent CLIs you already installed. Plans live in GitHub issues. Memory lives in a local SQLite file you can read and export. People who pick tools in 2026 ask who owns them. The honest answer here is you do.
