Other computers and SSH

There are two ways to use a second computer, such as a workstation or a Linux server: The computer owns its projects, files, worktrees, credentials, profiles and running work. In Settings, choose the computer under Settings on to edit its Providers and Agents.

There are two ways to use a second computer, such as a workstation or a Linux server:

  • Connect to another computer opens the whole Solenta on that computer in its own window. Its projects, threads, agents and worktrees stay there.
  • A remote project keeps one repo from that computer in this window. Git and the agent CLIs run there over SSH. It is described further down.

Add another computer

  1. Enable SSH on a Mac or Linux host. Use its SSH alias or user@host. Solenta asks for a password or host trust when needed.
  2. Open Settings > Connections, enter the SSH host, then press Check computer. This checks the existing server without installing or starting it.
  3. For a new host, press Prepare server. This downloads the standalone server for the host's OS and architecture, verifies its release checksum and sets up the supported user service. It bundles Node; no Electron, display server or preinstalled Node is required.
  4. Press Connect. Leave Token blank to read it over SSH. Show in sidebar adds that computer's projects and threads to this window. Connect also opens its own window.

The computer owns its projects, files, worktrees, credentials, profiles and running work. In Settings, choose the computer under Settings on to edit its Providers and Agents. Other client settings remain on this computer. A remote-only provider or a profile with the same name elsewhere keeps its own configuration. An offline computer cannot fall back to local settings.

Install Git and the agent CLIs on the host. The standalone archive does not include them or npm. In the remote window, open Settings > Providers to install or sign in with the existing provider terminal. Installation commands are shown for review before running. Sign-in and API keys belong to the host; connecting never copies this computer's provider credentials there.

You can also choose Address and paste a paired device link from an already running Solenta Web desktop or standalone server. Use HTTPS through Tailscale or your own trusted network route. An address connection does not install or start the endpoint. Windows desktop hosts can use this route; managed Windows background servers are not supported.

Connections shows the route, verified computer identity, runtime and known build, plus installed agents and their sign-in state. Unknown sign-in state means installed, not ready. Saved route tokens are encrypted using the system keychain. An older endpoint without computer identity needs explicit compatibility consent; a saved identity mismatch blocks the connection.

Disconnect removes this window's sidebar attachment and leaves remote work running. Forget removes the route and saved token; it does not uninstall or stop the server. Revoke a device on the host to remove that device's access. These are separate operations.

Standalone servers and user services

The standalone archive supports Linux and macOS on x64 and ARM64. A managed Linux installation uses systemd user services. Check the reported linger state: surviving logout or reboot depends on the host's user-service configuration. macOS uses launchd in the logged-in user's session, so it requires that login session. If a service manager is unavailable, choose External process under Prepare as. This explicitly starts an unsupervised server without a restart guarantee after logout or reboot. Automatic SSH preparation also reports which mode it could use. Existing external servers remain externally managed; preparation does not take over an already owned process.

Check computer reports whether the server is installed and running, its service manager and session limits. Managed servers expose Start and Recent logs here. Update uses the verified runtime: a Node server uses the server service updater, while a desktop runtime uses its own supported installer. Updates refuse to interrupt active work by default. A reconnect alone does not prove an update succeeded.

For manual administration, the server archive includes bin/solenta-server and bin/solenta-service. The service command separates install, status, logs, start, stop, restart, update and uninstall. Disconnecting a client never invokes these lifecycle actions.

If Connect fails

  • SSH login or trust: check ssh user@host and answer the password or trust prompt. Keep normal SSH host-key checking enabled.
  • Server unavailable: press Check computer, read Recent logs for a managed server, then Start server if it is stopped.
  • Identity changed: verify the target computer and route. A bound route cannot bypass a failed identity check by allowing legacy mode.
  • Agent unavailable or signed out: install and sign in on that computer through its Providers settings. A successful connection alone does not make an agent ready.
  • Offline: Retry reconnects the saved route. Local credentials and settings are never used as a substitute.

Remote projects

A project can also live on another machine while you stay in this window. Set remote host (user@host) and remote path when adding or editing the project, and every command Solenta would run locally is wrapped as: 

ssh -o BatchMode=yes -o ConnectTimeout=10 user@host 'cd /remote/path && claude ...'

The agent CLI executes on the remote and streams back over the pipe, so the UI looks exactly like a local run. Notes:

  • Auth is key-based only. BatchMode=yes never prompts for a password; a host you cannot key into fails fast.
  • The agent CLIs must be installed on the remote; local installs are not needed.
  • Worktree setup and pull are local-only in v1.
