# Run Solenta remotely by moving ownership

**T3 Code Connections attaches a client to another machine's complete execution environment.** The chosen host owns projects, threads, worktrees, provider processes, terminals, credentials, and durable state; the client retains a connection profile and renders the host's streams. T3 ships four ways to reach that same server: a paired direct endpoint, desktop-managed SSH forwarding, T3 Connect's account-assisted tunnel, and the local desktop server. The transport is interchangeable because an environment ID, rather than an endpoint or repository path, anchors identity. **Solenta's closest existing foundation is `--serve-web`, whose HTTP/WebSocket server already shares the desktop Store, Runner, and IPC handlers.** Its current SSH-project feature moves selected commands but leaves other app operations local, so extending that feature would preserve the wrong ownership boundary. The recommended first step is a real two-machine test of loopback `--serve-web` through SSH forwarding, followed by a native host switcher that reuses the wire API and scopes state by host. This report reflects T3's official source at commit [`54084ae`](https://github.com/pingdotgg/t3code/tree/54084ae1e6c32809db040e4fa571c80fdf2d8ae4), inspected as of 2026-10-02; its source paths are verified, but no live cross-machine T3 or Solenta session was measured.

## T3 makes the selected environment own every turn

In T3, **a connection is a route to one environment server, not a project-level SSH setting**. Its client model distinguishes Primary, Bearer, Relay, and SSH targets, while the server persists a UUID environment ID and advertises that ID, protocol version, platform, and capabilities. The client registry keys each connection and supervisor by environment ID, so a changed hostname or tunnel can still refer to the same environment. The server owns each project and its threads; matching Git remotes across machines do not move a thread from one environment to another. ([Target model](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/model.ts#L4-L54), [server identity](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/environment/ServerEnvironment.ts#L83-L226), [remote architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/remote.md#L1-L15))

The user adds an environment in Settings → Connections by pasting a pairing URL or entering a host and code; desktop also offers SSH. Saved environments reconnect at startup, can be disabled without deletion, and can be removed with their client-side credentials and caches. Desktop stores its connection catalog using Electron SafeStorage and atomic file replacement; the hosted browser client uses IndexedDB. **Connection selection changes where commands run, not merely which files appear in the UI.** T3's resolver checks the descriptor's environment ID and protocol compatibility, then opens the environment's `/ws` RPC session. A turn command reaches `OrchestrationEngine.dispatch`; the provider reactor starts and sends work through `ProviderService` using the host's CWD/worktree. Terminal and thread subscriptions return host snapshots plus updates. ([Connections UI](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/web/src/components/settings/ConnectionsSettings.tsx#L2328-L2397), [catalog](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/catalog.ts#L13-L55), [desktop storage](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/desktop/src/app/DesktopConnectionCatalogStore.ts#L380-L429), [resolver](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/resolver.ts#L248-L285), [turn execution](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L1493-L1527))

T3's server sends a lightweight global shell snapshot, while an opened thread gets its own detail subscription. The detail stream accepts `afterSequence`; the server attaches the live stream before replaying persisted events, and the client deduplicates overlap. This design matters for unstable remote links: reconnect can rebuild a view without fetching every transcript or silently missing the gap between snapshot and subscription. Optional client-side auto balance among grouped projects is a routing policy after multiple environments exist; draft placement stays stable and an existing thread stays on its original machine. **It is not required for remote execution.** ([Shell and detail routes](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/ws.ts#L2275-L2290), [gap-free replay](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/ws.ts#L2448-L2495), [HTTP snapshots](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/orchestration/http.ts#L31-L94), [auto balance guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#L48-L66))

## Four routes reach the same host process

T3 separates **reachability** from **authorization**. Direct LAN/private-network access requires the host to bind a reachable address and issue a pairing link. The bootstrap secret is placed in the URL fragment, expires after five minutes by default, and is atomically consumed; onboarding fetches `/.well-known/t3/environment`, checks compatibility, exchanges the code at `/oauth/token`, and saves the returned environment credential. The pairing link is therefore a host-control secret, even though it is short-lived. A Tailscale route can supply a private, HTTPS-reachable address. The hosted web app reaches that backend directly rather than proxying application traffic through its own website. ([Remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#L29-L100), [pairing parser](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/shared/src/remote.ts#L188-L245), [onboarding](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/onboarding.ts#L87-L130), [pairing grants](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/PairingGrantStore.ts#L375-L429))

Desktop SSH is operationally different but leads to the same environment protocol. T3 can install a pinned server archive under `~/.t3/runtime/versions/<version>` on Linux or Apple Silicon macOS, verify its `SHA256SUMS`, launch `t3 serve --host 127.0.0.1`, and forward a local port to the remote loopback port. It reuses a server that was already running and only stops a process it launched itself. OpenSSH keeps its normal host-key policy; the tunnel requests forward failure detection and keepalives. The remote shell must find the provider CLIs and credentials on the host. ([SSH installer and launch](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L449-L542), [forwarding](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L1139-L1163), [SSH guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#L103-L127))

T3 Connect adds a hosted discovery and reachability layer. Clerk identifies the account, a relay manages environment links and a Cloudflare tunnel, and the client obtains a one-time credential bound to its DPoP public key. The client exchanges that credential with the environment itself; the relay does not receive the resulting environment session token or proxy ordinary app HTTP/WebSocket calls. The relay signing key is still a trust root. This route avoids inbound router configuration but adds cloud services and a running host. **Inference for Solenta:** a self-hosted SSH or private-network route can ship independently of any Solenta-operated identity, relay, or tunnel fleet. ([T3 Connect architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/t3-connect.md#L1-L34), [discovery checks](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/relay/discovery.ts#L57-L92), [relay trust](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/t3-connect.md#the-relay-is-a-trusted-broker))

## Host authority and recovery determine safety

T3 does not treat network access as authorization. Its server issues sessions with declared scopes; an ordinary paired client can read and operate orchestration and terminals, while creating new pairing grants requires `access:write` and cannot delegate scopes the caller lacks. Sessions default to 30 days. A client fetches a five-minute WebSocket ticket through authenticated HTTP rather than putting its longer-lived token in the socket URL, and each RPC method has a required scope. Administrators can revoke both unused pairing links and active client sessions. **The effective security boundary is the host OS account:** an authorized client can run agents and terminals with access to that account's repository, shell, and provider credentials. A project label or worktree is organizational, not a filesystem sandbox. ([Scope definitions](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/contracts/src/auth.ts#L80-L116), [session lifetime](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/SessionStore.ts#L423-L424), [RPC authorization](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/RpcAuthorization.ts), [WebSocket upgrade](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/ws.ts#L4110-L4137), [workspace filesystem](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/workspace/WorkspaceFileSystem.ts#L117-L177))

T3 supervises each environment separately: transient failure backs off at 3, 4, 8, then 16 seconds, while authentication or configuration failure blocks until a new signal. A connection is ready only after socket authentication and an initial config snapshot matching the expected environment ID. Saved profiles and cached projections survive involuntary disconnect; subscriptions follow replacement sessions, but one-shot mutations are not automatically replayed. SSH reconnection can restore a stale port forward. These choices avoid both accidental cross-host display and duplicate commands after uncertain delivery. The host still must remain active: T3 documents systemd user service hosting on Linux, login-bound LaunchAgent hosting on macOS, and no Windows background service support. Host updates may interrupt agents and terminals; its thread continuation option is conditional and off by default. ([Supervisor](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/supervisor.ts#L692-L746), [ready handshake](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/rpc/session.ts#L213-L303), [connection runtime](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/connection-runtime.md#L5-L53), [background service guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/background-service.md#platform-support), [updating guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/updating.md#before-you-update))

Plain HTTP on a LAN supplies no transport confidentiality, even when the application authenticates requests. T3 recommends private-network or HTTPS routes for remote access. Its desktop stores credentials under OS-backed SafeStorage, whereas the standalone browser's IndexedDB catalog is available to code executing in that origin. **Inference for Solenta:** keep the initial server on loopback behind SSH, and audit both remote privileges and browser token handling before offering direct LAN binding. This report did not audit T3's full browser CSP, packet-level tunnel encryption, or live reconnect latency. ([T3 access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md), [desktop catalog](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/desktop/src/app/DesktopConnectionCatalogStore.ts#L380-L509), [web credential storage](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/web/src/connection/storage.ts#L539-L585))

## Solenta already has the remote server seam

Solenta's SSH project stores `remoteHost` and `remotePath` in a locally owned project and wraps selected provider/Git commands as `ssh ... 'cd <remotePath> && ...'`. The local Solenta process still owns the Store, Runner, UI, and most handler semantics. This split causes real gaps: `canHostWorktree` excludes SSH projects, so worker forks share the remote checkout; the built-in terminal chooses a local shell when the project is not WSL. Existing [issue #1402](https://github.com/currentbits/solenta/issues/1402) tracks the worker-isolation defect. **A remote environment with a local project on its own host avoids that project-level split**: provider, terminal, Git, Store, and worktree operations all execute together on the host. That is an implementation inference from the current code, and needs a two-machine test. ([Project type](/Users/willem/code/coder/src/shared/ipc.ts:18), [SSH wrapper](/Users/willem/code/coder/electron/ssh.js:99), [worktree gate](/Users/willem/code/coder/electron/services.js:1232), [terminal opening](/Users/willem/code/coder/electron/terminal.js:205))

`--serve-web` already moves this boundary as a unit. It starts an HTTP server and `/ws` bridge, defaults to `127.0.0.1:4620`, and passes the live desktop IPC context so browser calls reach the same `IPC_HANDLERS` that desktop IPC uses. A 32-byte persisted token authenticates the first WebSocket message, and the existing `createWireCoder` client handles retries and a `threads:list` resync. The app stays running after its last window closes in serve mode. A no-code deployment test can therefore run Solenta on a work machine with `--serve-web`, forward the port from the viewer with `ssh -N -L 4620:127.0.0.1:4620 user@work-machine`, and open `http://127.0.0.1:4620` on the viewer using the host's web token. The command is a proposed deployment pattern, **not an existing native Connections flow**. ([Web server](/Users/willem/code/coder/electron/webServer.js:1), [shared IPC bridge](/Users/willem/code/coder/electron/webBridge.js:105), [main wiring](/Users/willem/code/coder/electron/main.js:742), [wire reconnect](/Users/willem/code/coder/src/wireClient.ts:156), [last-window behavior](/Users/willem/code/coder/electron/main.js:1035))

Several differences from T3 remain material. Desktop `resolveCoderApi` always selects `window.coder` before the web transport; `useCoder` memoizes that API and persists boot/thread snapshots without a host key, so switching hosts in place could mix thread IDs and stale content. Web mode currently has **one broad bearer token, no TLS, and no per-handler scope boundary** beyond explicit simulator rejection; the browser stores the token in `localStorage`, and artifact GETs carry it in a query parameter. A desktop remote client also needs explicit semantics for viewer-local dialogs, notifications, updates, path opening, and simulator control. Finally, serve mode still creates an Electron window during boot, so a reliable displayless host is not established. These are current-code observations, not claims that a remote connection has been tested in production. ([API selection](/Users/willem/code/coder/src/coderApi.ts:77), [state snapshot](/Users/willem/code/coder/src/useCoder.ts:971), [boot snapshot store](/Users/willem/code/coder/src/bootSnapshot.ts:36), [token and LAN warning](/Users/willem/code/coder/electron/webServer.js:1), [bridge authorization](/Users/willem/code/coder/electron/webBridge.js:88), [browser token](/Users/willem/code/coder/src/coderApi.ts:19), [artifact URL token](/Users/willem/code/coder/electron/webServer.js:318), [window boot](/Users/willem/code/coder/electron/main.js:484))

## Ship a host switch before a relay

The implementation should stay under existing [issue #245](https://github.com/currentbits/solenta/issues/245), **Headless server mode and SSH remote environments**. [Issue #151](https://github.com/currentbits/solenta/issues/151) already covers QR pairing, one-time tokens, and revocable device sessions; it should own that later security/UX work rather than a duplicate Connections ticket. [Issue #1402](https://github.com/currentbits/solenta/issues/1402) remains the defect for existing SSH projects and should not be considered solved merely by adding host Connections. The following sequence is an implementation recommendation based on the T3 architecture and Solenta's current code.

| Stage | Minimal change | Acceptance check |
| --- | --- | --- |
| **0. Prove the boundary** | Run `--serve-web` on a second machine, keep it on loopback, forward over SSH, and register that machine's repository as a local project there. | From the viewer, add/open project, run an agent, fork a worker into a distinct remote worktree, answer a permission request, load an attachment/artifact, and reconnect after killing the forward. Confirm the worktree and provider process live on the host. |
| **1. Native desktop Connections** | Persist a small host catalog with stable host identity, label, SSH destination, and token reference. Electron main manages one local SSH forward per enabled host; the renderer selects `createWireCoder` for a chosen host. Reuse the current channel map and wire protocol. | A saved host reconnects after app restart and SSH drop. Its identity is checked before displaying cached data. Switching between two hosts never shows the other host's projects, threads, selected thread, or transcript. A failed command is reported once and is never replayed automatically. |
| **2. Secure and complete the route** | Store the remote credential in OS-backed storage, make host-side session revocation explicit, define viewer-local versus host-side native actions, and show actionable offline/auth/host-version states. Keep the server loopback-only during this stage. | Disconnect/revoke one client without affecting others; wrong-host and wrong-token paths fail closed; file/dialog/update actions target the intended machine; reconnect restores streams without duplicate turns. |
| **3. Unattended host only when needed** | Extract host startup from mandatory window creation and add a supported service/install flow. Consider direct HTTPS or account-assisted relay only after the loopback route works. | A rebooted host accepts a client without a GUI login where supported; interrupted turns and terminal sessions report their actual recovery state. |

Stage 1 needs an **environment identity handshake** even if its first version uses only SSH. A URL or local forwarded port is not an identity: both can be reused by another machine. It also needs a single retry owner and host-scoped caches, while the existing wire client's retry, queue limits, and `threads:list` resync can provide the first transport baseline. T3's cursor-based event replay suggests a later improvement if Solenta's patch gap/refetch path proves too expensive or lossy over real links; it is not a prerequisite for the first successful remote turn. ([T3 descriptor and resolver](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/resolver.ts#L248-L285), [T3 connection runtime](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/connection-runtime.md#L5-L53), [Solenta wire retry](/Users/willem/code/coder/src/wireClient.ts:24), [Solenta patch gap](/Users/willem/code/coder/src/useCoder.ts:1017))

The important unknowns are operational. There is no measured two-machine Solenta latency or bandwidth profile, no validated unattended host lifecycle, and no proof that every desktop-native action behaves correctly through the web bridge. T3's source inspection likewise did not include a live remote session. Stage 0 should answer those questions before committing to T3's larger SSH bootstrap installer or cloud relay. **Plain LAN exposure is premature** while Solenta's web API is token-wide and lacks TLS; the existing SSH forward already gives an encrypted reachability path with no new network service. ([Solenta web transport](/Users/willem/code/coder/electron/webBridge.js:139), [Solenta serve warning](/Users/willem/code/coder/electron/webServer.js:4), [T3 SSH route](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L1139-L1163))

## Conclusion

The key design choice is **where Solenta's state and execution live**. Treat another computer as a complete Solenta host and make the viewer a client of that host. That gives workers, worktrees, provider credentials, and transcripts one coherent owner, while SSH projects can remain a narrower feature with their own tracked limitations. The first deliverable is a measured, reproducible two-machine `--serve-web` session; the native Connections interface then turns that proven path into a saved, safe workflow. A relay and automatic balancing only become useful after host identity, reconnect, and lifecycle are dependable.
