# Solenta remote execution and Connections gap

## What can Solenta do today across machines?

### Takeaway

Solenta already has two distinct remote paths. An **SSH project** keeps the Solenta backend and data on the current computer and wraps selected Git/provider commands with SSH. **Web mode** keeps the entire Solenta backend on the work computer and exposes its existing API to a browser, which is the stronger foundation for a Connections feature.

### Inferences

- For one work machine and one viewing machine, start Solenta with `--serve-web` on the work machine and use `ssh -N -L 4620:127.0.0.1:4620 user@work-machine` from the viewer. Opening `http://127.0.0.1:4620` locally then routes the existing browser UI/API to the work machine; its projects should be registered as **local** projects on that host. This retains worktree/orchestration behavior because `remoteHost` is unset and Store/Runner/Git all execute there. The SSH tunnel is a proposed deployment pattern based on the loopback bind and shared backend, not an existing Solenta connection workflow. — [electron/webServer.js:23](../../electron/webServer.js#L23), [electron/main.js:755](../../electron/main.js#L755), [electron/services.js:1239](../../electron/services.js#L1239)
- Extending project-level SSH until it behaves like a remote Solenta host would require repairing many local assumptions (worktrees, terminal, repo actions, filesystem, provider configs). Reusing Web mode is smaller because it moves the entire ownership boundary together. — [electron/ipc.js:619](../../electron/ipc.js#L619), [electron/terminal.js:219](../../electron/terminal.js#L219), [electron/main.js:659](../../electron/main.js#L659)

### Gaps

- No live two-machine end-to-end test was run. The cited integration test uses real localhost sockets and a simulated run, not a remote production host. — [electron/test/web-integration.test.js:85](../../electron/test/web-integration.test.js#L85)
- Current `main.js` still calls `createWindow` during boot; `--serve-web` keeps a GUI app alive after closing windows, but the code does not prove operation on a displayless Linux server. — [electron/main.js:257](../../electron/main.js#L257), [electron/main.js:484](../../electron/main.js#L484), [electron/main.js:1035](../../electron/main.js#L1035)

## What must a native Connections feature add?

### Takeaway

The transport and domain API already exist, but the desktop renderer always takes its local preload bridge. A native Connections feature needs a host selection layer, a locally managed tunnel or secure transport, connection-scoped client state, and careful feature routing for machine-local actions.

### Cited Findings

- `resolveCoderApi` returns `window.coder` immediately on desktop, creating `createWireCoder` only when there is no preload bridge and a web token exists. `useCoder` memoizes its resolved API once and persists a single boot snapshot of projects, threads, and selected thread to browser storage. — [src/coderApi.ts:77](../../src/coderApi.ts#L77), [src/useCoder.ts:971](../../src/useCoder.ts#L971), [src/useCoder.ts:1051](../../src/useCoder.ts#L1051)
- The wire client has reconnect backoff, bounded queued invokes, invoke timeout, and a `threads:list` resync after reconnection. The wire protocol reuses the same channel names as Electron IPC and a web-safe push subset. — [src/wireClient.ts:24](../../src/wireClient.ts#L24), [src/wireClient.ts:60](../../src/wireClient.ts#L60), [src/wireClient.ts:101](../../src/wireClient.ts#L101), [src/wireClient.ts:156](../../src/wireClient.ts#L156), [src/shared/wire.ts:1](../../src/shared/wire.ts#L1)
- Web mode explicitly substitutes data URLs for local custom media URLs, excludes simulator push/control channels, and replaces native project picking with a typed path. A desktop renderer using a remote wire API cannot assume native app APIs refer to the remote host. — [electron/webBridge.js:143](../../electron/webBridge.js#L143), [electron/ipc.js:1607](../../electron/ipc.js#L1607), [src/shared/wire.ts:38](../../src/shared/wire.ts#L38), [test/webDegrade.test.tsx:82](../../test/webDegrade.test.tsx#L82)
- The current web server has **no TLS**, and an explicit `--serve-host` can widen the bind to a LAN address. The browser saves the bearer token in `localStorage`; artifact GETs put it in a query parameter. All post-auth IPC handlers are reachable except explicit simulator rejection, so the token grants broad authority. — [electron/webServer.js:4](../../electron/webServer.js#L4), [src/coderApi.ts:19](../../src/coderApi.ts#L19), [electron/webServer.js:318](../../electron/webServer.js#L318), [electron/webBridge.js:139](../../electron/webBridge.js#L139)
- The web bridge authenticates token equality and limits outbound buffered bytes, but the shown connection handler has no `Origin` check or per-client capabilities before invoking handlers. — [electron/webBridge.js:57](../../electron/webBridge.js#L57), [electron/webBridge.js:88](../../electron/webBridge.js#L88), [electron/webBridge.js:139](../../electron/webBridge.js#L139), [electron/webBridge.js:171](../../electron/webBridge.js#L171)

### Inferences

- **Milestone 0, no code:** Document and dogfood loopback `--serve-web` through SSH port forwarding. Verify project add, provider run, worker fork/worktree, permissions, attachments, image/artifact loading, and reconnect against a real second machine. A local project on the remote host is the correct test case. — [README.md:165](../../README.md#L165), [electron/test/web-integration.test.js:251](../../electron/test/web-integration.test.js#L251)
- **Milestone 1, native desktop switcher:** Persist a small list of host profiles (label, SSH destination, remote port, token reference), spawn an SSH local forward from Electron main with normal SSH host-key/key handling, and point one `createWireCoder` instance at its local forwarded port. Put the connection switch above `useCoder`; remount the app state on host change and key boot snapshots by host identity to prevent mixed threads. Reuse `IPC_HANDLERS`, `IPC_CHANNELS`, and `wireClient` rather than defining another RPC layer. — [electron/webBridge.js:8](../../electron/webBridge.js#L8), [src/shared/ipcChannels.ts:1](../../src/shared/ipcChannels.ts#L1), [src/useCoder.ts:971](../../src/useCoder.ts#L971)
- **Milestone 2, parity and security:** Route "open path", file dialogs, notifications, update controls, and other machine-local operations deliberately to viewer or host; avoid ambiguous defaults. Keep the server loopback-only behind SSH initially. Add per-connection revocation and a clear disconnected state; audit the wide web handler surface and token storage before any direct LAN/TLS offering. — [electron/ipc.js:1938](../../electron/ipc.js#L1938), [electron/webBridge.js:139](../../electron/webBridge.js#L139), [electron/webServer.js:4](../../electron/webServer.js#L4)
- **Milestone 3 only if needed:** Separate the host runtime from Electron window creation for unattended/headless use. This is larger than Connections itself and should follow a real requirement for headless deployment. — [electron/main.js:257](../../electron/main.js#L257), [electron/main.js:484](../../electron/main.js#L484)

### Gaps

- There is no measured latency/bandwidth profile for real cross-machine streaming, no demonstrated host startup/restart flow, and no two-host identity collision test. The current socket test only establishes local transport correctness. — [electron/test/web-integration.test.js:85](../../electron/test/web-integration.test.js#L85)
- A native client cannot be considered feature-complete by switching `resolveCoderApi` alone: `useCoder` keeps a memoized API and host-agnostic boot snapshot, while desktop-only actions still refer to the viewer's Electron process. — [src/useCoder.ts:971](../../src/useCoder.ts#L971), [src/useCoder.ts:1051](../../src/useCoder.ts#L1051), [electron/ipc.js:1938](../../electron/ipc.js#L1938)
