# T3 Code Connections architecture

## Which version and user-facing behavior were inspected?

### Takeaway
I inspected the official `pingdotgg/t3code` repository at commit `54084ae1e6c32809db040e4fa571c80fdf2d8ae4` (commit timestamp 2026-10-01 23:56:35 PDT; package behavior as found on 2026-10-02). Connections is a shipped Settings flow for attaching multiple execution environments to one client; remote work remains owned by the selected environment.

## What is a connection, and where is its identity and state stored?

### Takeaway
A connection is a client-side route to one server environment. The server persists an environment ID and owns project, thread, provider, filesystem, and execution state; the client persists route profiles and credentials under that environment ID.

### Cited Findings
- The target model has four variants: Primary (local desktop server), Bearer (paired direct endpoint), Relay (T3 Connect), and SSH. Persisted targets omit Primary; targets carry `environmentId` and label, while Bearer/SSH also carry a `connectionId`. — [model.ts, lines 4–54](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/model.ts#L4-L54)
- The saved profile stores HTTP and WebSocket base URLs for a paired bearer route, or an SSH target for an SSH route; the bearer credential is a separate record. `ConnectionCatalogEntry.enabled` keeps a saved connection switched off without removing it. — [catalog.ts, lines 13–55](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/catalog.ts#L13-L55)
- The catalog document groups persisted targets, profiles, bearer credentials, remote DPoP tokens, GitHub routing permissions, and disabled environment IDs. Explicit removal removes owned credentials and metadata. — [storageDocument.ts, lines 14–42](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/platform/storageDocument.ts#L14-L42); [lines 62–105](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/platform/storageDocument.ts#L62-L105)
- Desktop stores its catalog at `<stateDir>/connection-catalog.json`, encrypts the catalog through Electron SafeStorage, and writes by temporary-file rename. The hosted web client uses a browser IndexedDB database called `t3code:connection-runtime`, with catalog, shell, thread, config, and VCS stores. — [DesktopConnectionCatalogStore.ts, lines 220–264](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/desktop/src/app/DesktopConnectionCatalogStore.ts#L220-L264); [lines 380–429](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/desktop/src/app/DesktopConnectionCatalogStore.ts#L380-L429); [web storage.ts, lines 47–54, 136–160](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/web/src/connection/storage.ts#L47-L54)
- The server reads an environment ID file and, if missing, atomically creates a UUID; this identity is independent of URL/transport. The descriptor advertises server version, protocol version, platform, and capabilities. — [ServerEnvironment.ts, lines 83–179](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/environment/ServerEnvironment.ts#L83-L179); [lines 183–226](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/environment/ServerEnvironment.ts#L183-L226)
- Registry registration is keyed by environment ID, saves the registration, and creates a per-environment supervisor. Removing it closes the service scope, deletes catalog entry and cache, and disconnects a managed SSH route. Switching one off persists the flag, stops its supervisor, and tears down SSH tunnel while retaining credentials/cache. — [registry.ts, lines 437–483](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/registry.ts#L437-L483); [lines 657–715](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/registry.ts#L657-L715); [lines 745–805](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/registry.ts#L745-L805)
- The architecture explicitly states one environment owns its own projects and threads; repository identity may correlate clones but does not route a thread across environments. — [Remote architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/remote.md#L1-L15)

### Inferences
- `environmentId`, rather than endpoint string or repository path, is the durable foreign key a Solenta-style client would need for projects and threads. — [model.ts, lines 4–54](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/model.ts#L4-L54); [Remote architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/remote.md#L1-L15)

## How are environments discovered, paired, and reached?

### Takeaway
Direct pairing uses a short-lived bootstrap secret once to mint a saved environment session; SSH starts or reuses a server and tunnels its loopback port; T3 Connect discovers the server through a cloud relay but sends application traffic directly to a managed tunnel hostname.

### Cited Findings
- A pairing URL puts the token in the fragment. The parser accepts a full URL or host + code, derives HTTP and WS base URLs, and strips the token from normalized backend URLs. A hosted pairing URL keeps the backend host in query and token in fragment. — [remote.ts, lines 144–169](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/shared/src/remote.ts#L144-L169); [lines 188–245](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/shared/src/remote.ts#L188-L245)
- Direct onboarding fetches `/.well-known/t3/environment`, checks protocol compatibility, POSTs the pairing credential to `/oauth/token`, then registers a bearer profile and the returned access token under `bearer:<environmentId>`. — [onboarding.ts, lines 87–130](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/onboarding.ts#L87-L130); [descriptor.ts, lines 8–17](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/environment/descriptor.ts#L8-L17); [remote auth.ts, lines 115–140](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/authorization/remote.ts#L115-L140)
- Pairing links default to a five-minute expiry and are atomically consumed. Creating a link requires `access:write` and possession of every scope delegated; token exchange cannot widen scopes beyond the grant. — [PairingGrantStore.ts, lines 239–245, 375–429](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/PairingGrantStore.ts#L375-L429); [lines 512–532](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/PairingGrantStore.ts#L512-L532); [auth/http.ts, lines 400–418](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/http.ts#L400-L418); [EnvironmentAuth.ts, lines 804–823](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/EnvironmentAuth.ts#L804-L823)
- Desktop SSH mode calls its local SSH environment manager. A self-contained server archive is installed under `~/.t3/runtime/versions/<version>` on the remote, downloaded with curl/wget, checked against SHA256SUMS, and launched via `t3 serve --host 127.0.0.1`. The local SSH process forwards `<localPort>:127.0.0.1:<remotePort>`. An already-running server is reused and classified external; cleanup stops only a server managed by the SSH launcher. — [DesktopSshEnvironment.ts, lines 126–160](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/desktop/src/ssh/DesktopSshEnvironment.ts#L126-L160); [tunnel.ts, lines 449–542](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L449-L542); [lines 635–723](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L635-L723); [lines 1142–1163](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L1142-L1163); [SSH user guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#L103-L127)
- T3 Connect uses Clerk for identity and a relay to manage links, reachability, and tunnel allocation. A linked client's proof key obtains a one-time bootstrap credential through the relay, then the client exchanges it with the environment for a DPoP session. The relay never gets the environment session token and does not proxy normal app HTTP/WebSocket traffic. The client lists environments and verifies relay status/endpoint against the selected environment ID. — [T3 Connect architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/t3-connect.md#L1-L34); [discovery.ts, lines 57–92, 151–166, 261–270](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/relay/discovery.ts#L57-L92)

### Inferences
- Direct LAN/Tailscale pairing can be an incremental first release because they only require a reachable server and environment-issued auth. SSH adds lifecycle/port-forwarding; T3 Connect adds an operated relay, cloud identity, and managed tunnel infrastructure. — [Remote architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/remote.md#L1-L35); [T3 Connect architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/t3-connect.md#L1-L34)

### Gaps
- I did not execute T3 Connect against its production relay, so operational availability and paid service requirements are taken from the project's current code and documentation rather than live testing.

## What transport, protocol, event streaming, and execution boundary does it use?

### Takeaway
Every route resolves to the same environment HTTP origin and `/ws` typed RPC session. Commands execute on the environment server, and shell/thread streams come back from that server; transport choice does not move provider execution into the client.

### Cited Findings
- The connection resolver handles Primary, Bearer, Relay, and SSH separately, then re-fetches the environment descriptor, checks ID and protocol version, and appends `orchestrationProtocol` to the WebSocket URL. — [resolver.ts, lines 248–285](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/resolver.ts#L248-L285); [compatibility.ts, lines 9–29](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/compatibility.ts#L9-L29)
- Bearer/DPoP clients fetch a short-lived WebSocket ticket over authenticated HTTP, put `wsTicket` on `/ws`, and open a JSON RPC WebSocket. The server authenticates the upgrade before installing its `WsRpcGroup` handler. Each method maps to a required scope, including `orchestration.dispatchCommand` needing `orchestration:operate` and subscriptions needing `orchestration:read`. — [authorization/remote.ts, lines 161–223](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/authorization/remote.ts#L161-L223); [rpc/session.ts, lines 162–213](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/rpc/session.ts#L162-L213); [server/ws.ts, lines 4112–4155](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/ws.ts#L4112-L4155); [RpcAuthorization.ts, lines 19–33](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/RpcAuthorization.ts#L19-L33)
- An RPC session is not marked ready merely when the socket opens: it subscribes to server config and requires the initial snapshot with matching environment ID. The client driver reports preparing/opening/synchronizing before returning a ready lease. — [rpc/session.ts, lines 213–303](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/rpc/session.ts#L213-L303); [connection/driver.ts, lines 44–59](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/driver.ts#L44-L59)
- The client can dispatch orchestration commands over RPC or the scoped HTTP `/api/orchestration/dispatch` endpoint. On the server, dispatch reaches `OrchestrationEngine.dispatch`; `thread.turn.start` emits a turn-start intent, which the provider reactor handles by `ProviderService.startSession` (with remote CWD/worktree and runtime mode) and `ProviderService.sendTurn`. Thus provider processes run on the server host. — [server/ws.ts, lines 532–538, 2139–2174](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/ws.ts#L2139-L2174); [orchestration/http.ts, lines 96–125](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/orchestration/http.ts#L96-L125); [decider.ts, lines 1390–1467](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/orchestration/decider.ts#L1390-L1467); [ProviderCommandReactor.ts, lines 728–743, 1493–1527, 1825–1830](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts#L1493-L1527)
- `subscribeShell` and `subscribeThread` return a snapshot plus live updates. Thread detail can resume from `afterSequence`: server attaches live stream before replay/snapshot to avoid gaps, replays persisted events after the cursor, and client dedupes overlap by sequence. — [server/ws.ts, lines 2275–2290](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/ws.ts#L2275-L2290); [lines 2448–2495](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/ws.ts#L2448-L2495)

## How does reconnect and offline recovery work?

### Takeaway
One shared supervisor owns retries per environment. It retains registration and cached projections on involuntary disconnect, restores the route (including SSH forward), obtains fresh authorization/tickets as needed, opens a new RPC session, and resubscribes live streams.

### Cited Findings
- The supervisor's state distinguishes available, offline, connecting, backoff, connected, and blocked, with preparing/opening/synchronizing stages. Retry delays are 3, 4, 8, then capped at 16 seconds; a connection attempt has a 15-second establishment timeout. Authentication/permission/configuration errors become blocked and wait for a signal; transient failures back off. — [model.ts, lines 58–76, 128–147](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/model.ts#L58-L76); [supervisor.ts, lines 32–36, 104–106, 692–746](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/supervisor.ts#L692-L746)
- Foreground wakeups probe an established socket before replacing it; mobile can force replacement after a long background suspension. The RPC layer follows replacement sessions for subscriptions and does not automatically replay one-shot mutations. — [connection-runtime design, lines 5–19 and 39–53](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/connection-runtime.md#L5-L19); [rpc/client.ts, lines 117–152, 191–215](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/rpc/client.ts#L117-L152)
- The registry creates a supervisor once per environment and starts saved targets at app startup. Removal explicitly clears cached data; involuntary disconnect leaves the target registered. — [registry.ts, lines 278–319, 394–409](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/registry.ts#L278-L319); [connection-runtime design](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/connection-runtime.md#L17-L26)
- Cached shell/thread/config snapshots are keyed by environment in browser IndexedDB. Thread cache retains sequence so subscription can resume; the runtime design states a five-minute idle cache for thread details. — [web storage.ts, lines 47–77, 248–250](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/web/src/connection/storage.ts#L47-L77); [connection-runtime design](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/connection-runtime.md#L27-L45)
- SSH resolver calls `ssh.prepare` on each new connection attempt before bearer authorization; the SSH manager's `ensureTunnelEntry` restores launch/forward. Disabling or removing the SSH environment tears it down, while an external server survives. — [resolver.ts, lines 179–237](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/resolver.ts#L179-L237); [tunnel.ts, lines 1685–1717, 1720–1758](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L1685-L1758)
- Bearer/DPoP HTTP credentials are refreshed at HTTP request time without replacing a healthy WebSocket session. Credential expiry affects new requests/upgrades, not an already-authenticated open socket. — [connection-runtime design](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/connection-runtime.md#L19-L26); [environment-auth design](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/environment-auth.md#L20-L29)

### Inferences
- The recovery pieces T3 treats as essential are stable environment identity, a single retry owner, cursor-based stream resumption, and explicit process ownership for SSH. — [ServerEnvironment.ts, lines 83–179](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/environment/ServerEnvironment.ts#L83-L179); [supervisor.ts, lines 692–746](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/supervisor.ts#L692-L746); [server/ws.ts, lines 2448–2495](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/ws.ts#L2448-L2495); [tunnel.ts, lines 635–723](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L635-L723)
