# T3 Code Connections: security and operations

## Which product and revision did this research inspect?

### Takeaway
The official repository is `pingdotgg/t3code`; this note inspects `54084ae1e6c32809db040e4fa571c80fdf2d8ae4`, the repository HEAD fetched on 2026-10-02. All code links below pin that commit.

### Cited Findings
- The repository documents direct pairing, Tailscale HTTPS, T3 Connect, and desktop-managed SSH as ways to connect another device to the host environment. — [Official remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md)
- A connection is HTTP plus WebSocket to **one environment server**; that server owns provider execution, files, and durable state. A project and its threads remain on one environment. — [Remote architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/remote.md)

### Inferences
- The transferable feature is an environment server and client connection registry, not a remote shell bolted onto each provider. This follows from the shared transport and single-environment ownership described above.

### Gaps
- I did not run a live T3 host/client pair; operational behavior below is from code and official docs, not a network capture.

## How do clients pair, authenticate, and retain secrets?

### Takeaway
The environment issues its own scoped sessions. Direct pairing uses a short one-time bootstrap credential; T3 Connect brokers a DPoP-bound credential, then the client authenticates directly with the environment. Cloud identity does not replace environment authorization.

### Cited Findings
- Default one-time pairing tokens have a five-minute TTL; the generator uses 12 characters from an ambiguity-reduced alphabet. A successful database update marks a token consumed atomically, requiring it to be unexpired, unrevoked, unused, and proof-key-matched when bound. — [PairingGrantStore](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/PairingGrantStore.ts#L239-L280), [AuthPairingLinks](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/persistence/AuthPairingLinks.ts#L160-L181)
- The server stores pairing credentials in its `auth_pairing_links` database row; the access read model omits the recoverable secret, and only link creation returns it. — [AuthPairingLinks](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/persistence/AuthPairingLinks.ts#L130-L161), [Environment auth design](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/environment-auth.md)
- Default paired-client scopes include orchestration read/operate, terminal operate, review write, and relay read. Access management (`access:read/write`) and relay write are administrative scopes. Issuing another pairing credential requires `access:write` and possession of every delegated scope. — [Auth scopes](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/contracts/src/auth.ts#L80-L116), [Auth HTTP handlers](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/http.ts#L380-L432)
- Ordinary sessions use browser cookies, bearer tokens, or DPoP access tokens. Sessions default to 30 days; HTTP grants five-minute WebSocket tickets so the long-lived bearer/DPoP token is not put in the socket URL. Each RPC has a declared required scope; the WebSocket upgrade authenticates first. — [SessionStore](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/SessionStore.ts#L423-L424), [RPC authorization](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/RpcAuthorization.ts), [WebSocket route](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/ws.ts#L4110-L4137)
- Authorized administrators can revoke unconsumed pairing links and client sessions; removing a connection from one client merely forgets that local entry. — [Auth HTTP handlers](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/http.ts#L430-L510), [Remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#manage-or-revoke-access)
- Desktop saves the entire connection catalog, including credentials, through Electron `safeStorage` encryption and refuses persistence when encryption is unavailable. Mobile uses `expo-secure-store`. Standalone hosted web writes its connection catalog, including credentials, to origin-scoped IndexedDB, while its DPoP proof key is kept in a separate IndexedDB database. — [Desktop catalog](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/desktop/src/app/DesktopConnectionCatalogStore.ts#L380-L509), [Mobile catalog](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/mobile/src/connection/catalog-store.ts), [Web storage](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/web/src/connection/storage.ts#L289-L310), [Web credential store](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/web/src/connection/storage.ts#L539-L585), [Browser DPoP key](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/web/src/cloud/dpop.ts#L28-L109)
- Hosted pairing links put the backend host in the URL query but the secret in the fragment, and the browser removes the fragment after exchange. — [Hosted pairing code](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/web/src/hostedPairing.ts#L51-L84), [Remote architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/remote.md#hosted-web-is-a-client)

### Inferences
- A standard paired device is powerful: it can start agent operations and interactive terminal sessions on the host, although it cannot issue new pairing links or manage relay exposure without additional scopes. Treat the pairing URL as a host-control secret. — [Auth scopes](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/contracts/src/auth.ts#L80-L116), [RPC authorization](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/RpcAuthorization.ts)
- The browser's IndexedDB catalog is accessible to JavaScript in that origin; desktop and mobile have OS-backed storage. This makes web origin integrity and XSS prevention especially consequential. — [Web storage](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/web/src/connection/storage.ts#L289-L310), [Desktop catalog](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/desktop/src/app/DesktopConnectionCatalogStore.ts#L380-L509)

### Gaps
- I did not audit XSS defenses or the full browser CSP. I cannot claim the web catalog is resistant to in-origin script compromise.

## What are the network routes and their trust boundaries?

### Takeaway
Direct LAN needs a reachable host and gives the application its own authentication; Tailscale Serve supplies tailnet HTTPS; SSH forwards loopback; T3 Connect uses Cloudflare tunnels plus a Clerk-backed broker. None of these moves provider execution off the chosen environment.

### Cited Findings
- The desktop host requires Network access enabled (which restarts it), or a CLI host can bind `t3 serve --host <private-ip>`. Pairing persists client authorization. A loopback URL cannot reach another device. — [Remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#pair-over-a-lan-or-private-network)
- Tailscale Serve offers `https://machine.tailnet.ts.net/`; `t3 serve --tailscale-serve` or `t3 pair --tailscale` configures it. The hosted web app requires an HTTPS-reachable backend and connects to it directly, without proxying through `app.t3.codes`. — [Remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#tailscale-https), [Remote architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/remote.md#hosted-web-is-a-client)
- SSH launches or reuses a server, then forwards `localPort:127.0.0.1:remotePort` and exposes local `http://127.0.0.1:<port>/` / `ws://...` to the renderer. It sets `ExitOnForwardFailure=yes`, keepalives, and disables multiplexed control persistence; no custom `StrictHostKeyChecking` override appears in SSH arguments, so system OpenSSH policy applies. — [SSH tunnel](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L1139-L1162), [SSH base args](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/command.ts#L100-L113), [SSH local endpoint](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L1494-L1539)
- SSH's first managed launch downloads a pinned server archive into `~/.t3/runtime`, checks the release's `SHA256SUMS`, verifies the executable runs, and uses a staging/install marker. It supports remote Linux or Apple Silicon macOS; the remote provider CLIs must be available in a non-interactive login shell. — [SSH runtime installer](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L444-L535), [Remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#desktop-managed-ssh)
- T3 Connect uses Clerk cloud identity and a relay to authorize environment links and allocate a managed Cloudflare tunnel. The relay asks the linked environment for a one-time credential bound to a client's DPoP public key, but the client exchanges it with the environment directly. The Worker does not proxy ordinary app HTTP/WebSocket traffic. Managed tunnel origins must be loopback. — [T3 Connect architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/t3-connect.md), [Cloud origin validation](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/cloud/http.ts#L333-L364), [Relay connector](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/infra/relay/src/environments/EnvironmentConnector.ts)
- The relay's signing key remains a trust root; DPoP prevents credential reuse but does not neutralize a compromised relay signing key. — [T3 Connect architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/t3-connect.md#the-relay-is-a-trusted-broker)

### Inferences
- Plain HTTP over LAN has no application transport encryption. Use a private tunnel or HTTPS where confidentiality matters; T3's pairing/session authentication does not itself encrypt packets. — [Remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#hosted-web-app)
- T3 Connect avoids opening an inbound router port but adds dependence on Clerk, the relay, Cloudflare, and a live host; SSH avoids those cloud services but requires SSH accounts/keys and desktop-managed lifecycle. — [T3 Connect architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/t3-connect.md), [Remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md)

### Gaps
- I did not confirm packet-level TLS termination or Cloudflare edge-to-host cipher behavior. The official docs identify the tunnel and HTTPS hostname, but do not claim end-to-end encryption under keys owned solely by the client and host.

## What can remote clients do, and how does the system fail or recover?

### Takeaway
The environment server is the effective filesystem and process boundary. Connections are supervised and can reconnect, but the host must stay running, and server updates can interrupt turns and terminals.

### Cited Findings
- The RPC scope map grants `orchestration:operate` to dispatch commands, provider setup, project writes, Git/worktree changes and preview control; `terminal:operate` governs opening and writing terminals. The same map assigns read scopes to project listings and reads. — [RPC authorization](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/RpcAuthorization.ts)
- Workspace-relative writes are checked against root escape, but authorized absolute-path reads can read any regular host file accessible to the server account (up to 1 MiB per read). Projects are organizational, not filesystem sandboxes. — [WorkspaceFileSystem](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/workspace/WorkspaceFileSystem.ts#L1-L16), [absolute read resolution](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/workspace/WorkspaceFileSystem.ts#L117-L177), [Environment auth design](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/environment-auth.md#the-environment-is-the-filesystem-boundary)
- Server secrets are file-backed under a `0700` directory, files are chmod `0600`, and writes use a temporary file plus rename. Provider credentials and agent work stay on the remote host. — [ServerSecretStore](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/ServerSecretStore.ts#L126-L190), [Remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#desktop-managed-ssh)
- The connection supervisor uses 3/4/8/16-second retry delays, 15-second establishment/probe timeouts, network status, and wakeup signals. SSH reconnect checks existing forward readiness and recreates stale tunnels; disconnect only stops a managed server it owns. — [Connection supervisor](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/client-runtime/src/connection/supervisor.ts#L28-L47), [SSH tunnel manager](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/packages/ssh/src/tunnel.ts#L1608-L1657), [Remote architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/remote.md#access-and-process-ownership-are-different)
- Linux background hosting uses a systemd user service with lingering; macOS LaunchAgent hosting lasts only while logged in and awake; Windows background services are unsupported. Saving T3 Connect login alone does not start the host. — [Background service guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/background-service.md#platform-support), [Remote-access guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#t3-connect)
- Server update restarts may interrupt agents and terminals. `Continue threads after restarts` is off by default, requires host support and host startup, and cannot always recover a provider session. Clients must tolerate older servers by capability detection. — [Updating guide](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/updating.md#before-you-update), [Remote architecture](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/remote.md#access-and-process-ownership-are-different)
- T3 Connect's host-side startup retries temporary relay failures up to ten minutes. Idle tunnel reclamation is configurable and defaults off at deploy time; recoverable hosts can restore their tunnel while preserving hostname. — [Remote troubleshooting](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/user/remote-access.md#t3-connect-troubleshooting), [T3 Connect lifecycle](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/docs/internals/t3-connect.md#idle-tunnels-are-reclaimed-and-recovered)

### Inferences
- The security principal is the server OS user. Remote work can reach that user's provider credentials, Git authentication, filesystem and shell. A project/worktree selection does not confine a client or agent. — [WorkspaceFileSystem](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/workspace/WorkspaceFileSystem.ts#L1-L16), [RPC authorization](https://github.com/pingdotgg/t3code/blob/54084ae1e6c32809db040e4fa571c80fdf2d8ae4/apps/server/src/auth/RpcAuthorization.ts)

### Gaps
- I did not test active-turn recovery after process failure or measure reconnect latency. The documented continuation semantics should be treated as conditional, not a guarantee.
